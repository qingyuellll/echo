# ADR-001：采用本地事务，跨库一致性交给消息补偿

- 状态：已接受
- 日期：2026-09-28
- 影响范围：订单创建、库存扣减、座位占用、秒杀落单

## 一、背景

下单链路需要同时写入多类数据：订单主表、座位状态、票种库存、预订单、积分流水。这些数据当前全部位于同一个 MySQL 库 `echo`，由同一个 `DataSource` 与同一个事务管理器管理。

秒杀链路在 Redis 侧完成库存判断与扣减，再由消费者异步写入 MySQL。Redis 与 MySQL 分属两类存储，天然无法置于同一个本地事务。

## 二、决策

1. 库内一致性使用 Spring 的本地事务（`@Transactional`），订单、座位、库存的写入放在同一事务中。
2. Redis 与 MySQL 之间的一致性使用「本地事务 + 消息补偿」：Redis 侧 Lua 保证库存判断与扣减的原子性，落库动作由 `SeckillOrderConsumer` 异步完成，失败由定时任务核对并回滚。
3. 引入分布式事务框架的配置位保留在 `application-seata.yml.disabled` 与 `pom.xml` 的注释依赖中，当前不启用。

## 三、理由

**单一数据源**：业务数据集中在 `echo` 库，跨库写入的场景尚未出现。本地事务在这种结构下提供最强的隔离性与最简单的故障模型，事务失败即回滚，无需协调者参与。

**性能**：本地事务只有一次数据库开销。Seata AT 模式需要额外维护 undo_log、开启全局锁、两次提交，秒杀这类高并发写入场景的延迟会显著上升。

**故障面**：分布式事务引入 TC（事务协调者）成为新的单点，TC 不可用时全局事务阻塞。本地事务的故障面仅限数据库本身，运维成本更低。

**与现有补偿机制配合**：秒杀链路已经具备三层补偿——`SeckillQueueConsumer` 异步落单、`PreOrderTimeoutScheduler` 超时回滚、`RedisCompensateTaskScheduler` 库存核对。这三层覆盖了 Redis 与 MySQL 的差异窗口，无需额外的全局事务保证。

**异步语义匹配业务**：秒杀接口返回「已受理」而非「已成交」，用户轮询排队结果。这个交互模型本身接受短暂不一致，与本地事务加补偿的组合天然契合。

## 四、Seata 的适用条件

Seata 解决的是跨服务、跨库的原子提交。当前架构满足以下任一条件时，才需要重新评估：

1. 业务库按领域拆分为多个物理库（订单库与库存库分离），且要求强一致。
2. 下单链路拆分为独立微服务，服务之间需要原子提交。
3. 引入第三方支付或外部库存系统，需要与外部系统保持一致。

单机吞吐不构成引入 Seata 的理由：吞吐瓶颈通过加实例、拆读库、缓存前置解决，分布式事务只会增加开销。

## 五、升级路径

需要启用 Seata 时按以下顺序执行：

1. 放开 `echo/pom.xml` 中 `seata-spring-boot-starter` 的注释。
2. 把 `application-seata.yml.disabled` 重命名为 `application-seata.yml`，按部署环境填写 `seata.server` 地址。
3. 部署 Seata Server（file 或 db 模式），确保 TC 可用。
4. 为需要跨库原子提交的方法加 `@GlobalTransactional`，方法内部保持本地事务。
5. 压测对比启用前后的 P99 与吞吐，确认收益大于开销。

## 六、影响

正向影响：

- 下单与秒杀的事务边界清晰，事务内容易读。
- 无需维护 Seata Server，部署结构简单。
- 故障定位只需关注数据库与补偿任务的日志。

需要持续关注：

- 补偿任务的执行结果依赖监控，`pre_order_compensation_fail_total`、`redis_compensation_fail_total`、`seckill_reconcile_orphans_found_total` 是核心观测指标。
- 异步落单存在秒级延迟，前端以轮询排队结果的方式呈现。
