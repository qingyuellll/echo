# Echo 性能压测报告

> 测试时间：2026-11-10 11:00 – 12:10
> 被测系统：Echo 演出票务平台（Spring Boot 2.7.18 / JDK 17，单实例，端口 8081）
> 压测工具：Apache JMeter 5.6.3（命令行非 GUI 模式）、Node 原生压测器
> 脚本位置：`jmeter/`，原始结果：`jmeter/bench/*.jtl`

## 一、结论速览

| 指标 | 实测值 | 测试条件 |
|---|---|---|
| 读接口混合吞吐 | **1600 req/s**（饱和） | 4 个读接口混合，200 并发，P90 268ms |
| 读接口最佳响应 | 1257 req/s / P90 72ms | 50 并发 |
| 秒杀入口瞬时承载 | **500 并发全量受理，零超卖** | 库存 500，一次性涌入，P90 324ms |
| 秒杀入口持续吞吐 | **434 req/s** | 500 并发 × 5 轮（2500 请求，含售罄拒绝流量） |
| 秒杀入口峰值吞吐 | **1919 req/s**，3 万请求 25.6 秒打完 | 1000 账号 × 30 轮，并发 1000 |
| 3 万请求漏斗 | 拒绝 25,743 / 入队 4,257 / 成交 1,000 | 库存 1000，最终 96.7% 请求被挡在成交之外 |
| 秒杀链路单请求耗时 | P50 21–28ms | 库存充足、不带登录 |
| 完整秒杀链路（含登录） | 500 并发 → 500 单全受理，整轮 19.5s | 登录是瓶颈，秒杀链路本身开销很低 |

结论：单机读路径在 1600 QPS 处饱和；秒杀入口峰值 1919 req/s，3 万请求里 96.7% 被限流或售罄挡住，1000 单全部成交且库存零误差；端到端的主要成本在登录的 BCrypt 哈希，秒杀链路本身开销很低。

## 二、测试环境与方法

### 2.1 环境

| 项 | 配置 |
|---|---|
| 机器 | i5-13500HX（20 逻辑核）/ 16GB |
| 部署形态 | **单机混布**：应用、MySQL、Redis、RocketMQ、JMeter 在同一台机器 |
| 后端 JVM | 默认堆，未做 GC 调优 |
| 数据库连接池 | HikariCP maximum-pool-size=20 |
| 秒杀限流配置 | JVM 令牌桶 2000 容量 / 1000 每秒；用户 5 次/秒；全局 5000 次/秒 |

单机混布意味着压测工具与被测应用争抢同一份 CPU，测出的是保守下限；压测机与应用分离时数值更高。

### 2.2 测试方法要点

1. **稳态压测**：`rampup=2s` 快速到满并发，`loops=50` 保证采样窗口足够长，吞吐只统计稳态段。
2. **断言区分业务拒绝与故障**：秒杀接口的「售罄 / 已购买 / 频繁 / 已结束」属于正常业务结果，计入通过；HTTP 非 200 或无法识别的响应体记为失败。
3. **数据准备幂等**：每轮压测前执行 `prepare-seckill.sql`（时间窗与库存）与 `reset-seckill.cmd`（清库存、已购集合、排队、幂等键）。
4. **一致性校验**：每轮结束比对 `seckill:stock` 剩余值、`seckill:order` 集合人数、受理请求数三者是否一致。

### 2.3 测试数据

- 压测账号：`19900000001` – `19900001000`（1000 个，密码 123456），一次性插入，便于识别与清理。
- 目标票种：`ticket_id = 8`，秒杀库存按轮次设为与并发数相等。

## 三、读路径压测

场景：`/show/search`、`/show/{id}`、`/ticket/detail/{id}`、`/show-review/hot` 四个接口按 1:1:1:1 混合，每线程 50 轮。

| 并发 | 请求数 | 吞吐 | 平均 | P50 | P90 | P99 | 错误率 |
|---|---|---|---|---|---|---|---|
| 50 | 10,000 | 1257 req/s | 32ms | 26ms | 72ms | 113ms | 0% |
| 100 | 20,000 | 1523 req/s | 57ms | 43ms | 135ms | 233ms | 0.04% |
| 200 | 40,000 | **1662 req/s** | 111ms | 82ms | 268ms | 483ms | 0.02% |
| 400 | 80,000 | 1602 req/s | 240ms | 203ms | 416ms | 729ms | 0.003% |

**拐点判断**：并发从 200 翻到 400，吞吐从 1662 回落到 1602，P90 从 268ms 涨到 416ms，平均耗时翻倍。请求开始排队，增加并发只增加延迟。

**饱和点**：单机读路径约 **1600 req/s @ 200 并发**。

**失败样本**：9 次业务失败（0.02%），均为 `/show/{id}` 返回 200 但 `success=false`。离线用 2000 次同接口请求（100 并发）复测未复现，列为待观察项。

## 四、秒杀链路压测

秒杀链路：`POST /ticket-order/seckill/{ticketId}` → 本地令牌桶 → 用户级与全局限流 → 票种与时间窗 → 下单频控 → 信誉分 → 一人一单预检 → 入队 → 队列消费时 Lua 扣减库存 → 异步建预订单。

为分离「登录开销」与「秒杀链路开销」，分两组测试。

### 4.1 剥离登录：秒杀纯链路（预登录 token）

先用 500 个账号批量登录拿到 token（`gen-tokens.js`），压测时直接带 token 打秒杀入口。

| 并发 | 受理单数 | 吞吐 | 平均 | P90 | P99 | Max | 库存 / 已购集合 |
|---|---|---|---|---|---|---|---|
| 100 | 100 / 100 | 36/s | 33ms | 77ms | 169ms | 169ms | 0 / 100，一致 |
| 300 | 300 / 300 | 108/s | 30ms | 56ms | 113ms | 115ms | 0 / 300，一致 |
| 500 | 500 / 500 | 191/s | 112ms | 324ms | 490ms | 501ms | 0 / 500，一致 |

吞吐数值含 3 秒爬坡，单轮请求量等于并发数，持续能力看下面的 500 并发 × 5 轮。

**持续压测**（500 并发 × 5 轮 = 2500 请求，库存 500）：

| 指标 | 数值 |
|---|---|
| 吞吐 | **434 req/s** |
| P50 / P90 / P99 | 715ms / 904ms / 1002ms |
| 失败率 | 0% |
| 结果分布 | 前 500 单受理成功，其余 2000 次命中售罄与已购买拒绝路径 |

这组数据说明秒杀入口在库存售罄后仍能持续处理拒绝流量，这正是真实秒杀（95% 以上请求注定失败）的压力形态。

### 4.2 完整链路：含登录

每线程先用 CSV 中的账号登录（BCrypt 校验），再打秒杀。

| 并发 | 登录 P50 | 秒杀 P50 | 秒杀 P90 | 整轮耗时 | 受理 | 库存一致性 |
|---|---|---|---|---|---|---|
| 100 | 785ms | 24ms | 229ms | 5.3s | 100 / 100 | 一致 |
| 300 | 7,066ms | 2,427ms | 4,854ms | 12.0s | 300 / 300 | 一致 |
| 500 | 12,516ms | 3,085ms | 11,104ms | 19.5s | 500 / 500 | 一致 |

三组的库存扣减、已购集合人数、受理请求数完全相等，超卖、漏扣、重复受理均未出现。

## 五、秒杀入口分层压测（3 万请求）

前面的测试验证了「500 并发能全部受理」，请求量未触及限流阈值。本节把请求量放大到 3 万，观察请求在各层闸门上的分布。

### 5.1 测试方法

- 账号池：1000 个压测账号（199 号段），先批量登录拿到 token，压测时直接带 token 打入口，剥离登录开销。
- 压测器：`jmeter/burst-seckill.js`（Node 原生 http，keep-alive，并发 worker 抢任务队列）。
- 判定方式：解析每个响应的 `success` 与 `message`，落到具体闸门，HTTP 状态码作为辅助判断。

秒杀入口的校验顺序（从外到内）：

```
JVM 本地令牌桶(2000 容量 / 1000 每秒)
  → 用户级限流(5 次/秒)
  → 全局限流(5000 次/秒)
  → 票种与活动时间窗
  → 下单频控(rate:order)
  → 信誉分
  → 一人一单预检(Redis Set)
  → 售罄快速判断
  → 入队(ZADD seckill:queue)
  → 队列消费时 seckill.lua 扣减库存
```

### 5.2 3 万请求的漏斗

1000 账号 × 30 轮 = 30,000 请求，并发 1000，库存 1000：

| 结果 | 数量 | 占比 | 说明 |
|---|---|---|---|
| 拒绝-下单频控「操作过于频繁」 | 17,897 | 59.7% | 同一用户短时间内重复下单，被 `rate:order` 挡住 |
| 拒绝-本地令牌桶「当前请求过多」 | 7,104 | 23.7% | 超过 1000 次/秒的部分拿不到令牌 |
| 入队「QUEUED」 | 4,257 | 14.2% | 拿到令牌且通过业务校验，进入排队 |
| 拒绝-一人一单 | 742 | 2.5% | 已成交用户重复请求 |
| **合计** | **30,000** | **100%** | |

性能指标：墙钟 25.63 秒，平均 **1170 req/s**，峰值 **1919 req/s**，P50 842ms / P90 1210ms / P99 1620ms。

**最终成交 1,000 单**（库存 1000 全部售出），3 万请求中 96.7% 被挡在成交之外，与真实秒杀的形态一致。

### 5.3 极限瞬时：3000 并发一次性涌入

1000 账号 × 3 轮 = 3000 请求，并发 3000，库存 3000：

| 结果 | 数量 | 占比 |
|---|---|---|
| 入队 QUEUED（返回 `ahead` 位次，如 `ahead=6`） | 2,973 | 99.1% |
| 拒绝-一人一单 | 25 | 0.8% |
| 拒绝-下单频控 | 2 | 0.1% |

峰值 3000 req/s，P50 3,492ms / P90 4,961ms。令牌桶在这轮拒绝了 0 个请求：容量 2000 加上运行 5.5 秒补充的约 5500 个令牌，足以吸收这次突发。令牌桶的语义是吸收瞬时突发、限制持续速率，不是按并发数拒绝。

### 5.4 三层限流各自的证据

| 闸门 | 配置 | 验证方式 | 实测结果 |
|---|---|---|---|
| JVM 本地令牌桶 | 容量 2000，1000 个/秒 | 3 万请求持续 25.6 秒，理论可发放 2000 + 1000×25.6 ≈ 27,600 个令牌 | 28,896 个请求拿到令牌、7,104 个被拒，拒绝数与令牌缺口吻合 |
| 用户级限流 | 5 次/秒/用户 | 单账号 1 秒内连打 20 次 | 5 次通过、15 次「1秒内最多5次」，精确命中 5/s |
| 全局限流 | 5000 次/秒 | 单机压测峰值 1919 req/s | 未触发，属预期；验证需要多台压测机或临时降低阈值 |
| 下单频控 | 5 次/TTL/用户 | 3 万场景中重复下单 | 17,897 次「操作过于频繁」 |
| 一人一单 | Redis Set | 已成交用户重复请求 | 742 + 25 次「您已购买过该秒杀票」 |

### 5.5 一致性校验

3 万请求跑完、等待队列消费完毕后：

| 项目 | 值 |
|---|---|
| 剩余库存 `seckill:stock:8` | 0 |
| 已购集合 `seckill:order:8` | 1000 人 |
| 排队队列 `seckill:queue:8` | 0 |
| 活跃队列标记 | 空 |
| 成交单数 | 1000 |

库存扣减数、已购集合人数、实际成交数三者完全一致，超卖与「扣减后未入集合」的脏数据均未出现。

压测刚结束时读库存会看到剩余 23，那是队列仍在消费（异步入队、异步扣减），等队列排空后归零。一致性校验的时机是 `seckill:queue:{ticketId}` 归零之后。

## 六、瓶颈定位

| 现象 | 原因 |
|---|---|
| 读路径 200→400 并发吞吐不涨、延迟翻倍 | 单机 CPU 与连接池饱和，请求排队；HikariCP 上限 20 连接是结构性约束 |
| 含登录压测 500 并发时登录 P50 达 12.5 秒 | 登录走 BCrypt cost=12，单次约 300–500ms CPU。500 次 × 0.5s ÷ 20 核 ≈ 12.5s，与实测吻合 |
| 登录剥离后秒杀 P50 回到 21–28ms | 秒杀链路是 Redis Lua 加内存判断，不访问数据库，成本极低 |
| 秒杀持续压 434 req/s | 每单都要写队列并异步建预订单，且含 2000 次拒绝路径的 Redis 交互；压测工具与应用争抢同一 CPU |

成本集中在「密码哈希」与「单机资源」，秒杀扣减不是热点。这也解释了登录接口配置图形验证码与频控的原因：它是单位成本最高、最容易被刷的接口。


## 八、局限与后续

1. **单机混布**：压测工具与应用争抢 CPU，吞吐是保守下限；要更接近真实需把压测工具放到另一台机器。
2. **JVM 未调优**：使用默认堆与 GC 参数，未做 G1 调优对比。
3. **缺少系统级曲线**：本轮用延迟与吞吐曲线加理论推算定位瓶颈，CPU、GC、连接池曲线可通过 `/actuator/prometheus` 接入 Prometheus 后补齐。
4. **`/show/{id}` 偶发 0.02% 业务失败**：未复现，列为待观察项。
5. **压测账号**：1000 个测试账号（199 号段）保留在库中便于复测，清理脚本见 `jmeter/cleanup-bench-users.sql`。
